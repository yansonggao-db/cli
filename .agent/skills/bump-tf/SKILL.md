# Bump Terraform Provider

Bumps the pinned Databricks Terraform provider, regenerates everything derived from
its schema, fixes any acceptance tests the schema change breaks, and opens a PR.

The provider version is the single source of truth in
`bundle/internal/tf/codegen/schema/version.go`. Everything else
(`bundle/internal/tf/schema/*`, `bundle/internal/tf/schema/root.go`,
`bundle/terraform_dabs_map/generated.go`) is generated from it.

## Arguments

Parse the user's input for the target version:

- An explicit version (e.g. `1.122.0`, with or without a leading `v` — strip it).
- `latest` / no version → resolve the latest GitHub release (Step 1).

## Workflow

### Step 1: Resolve the target version

Read the current version from `bundle/internal/tf/codegen/schema/version.go`
(the `const ProviderVersion = "X.Y.Z"` line).

If the user gave an explicit version, use it. Otherwise resolve the latest:

```bash
gh api repos/databricks/terraform-provider-databricks/releases --jq '.[0].tag_name' | sed 's/^v//'
```

Confirm the target release exists on GitHub (this also gives you the publish time):

```bash
gh api repos/databricks/terraform-provider-databricks/releases/tags/v{version} --jq '.published_at'
```

If the tag does not exist on GitHub, stop and report — you cannot bump to a version
that was never released.

### Step 2: Bump the version constant

Edit `bundle/internal/tf/codegen/schema/version.go` and set
`const ProviderVersion = "{version}"`.

Do **not** hand-edit `bundle/internal/tf/schema/root.go` — its `ProviderVersion`
constant is regenerated by codegen in Step 4.

Do **not** touch the `// Matches databricks-tf-provider/1.121.0` comment in
`libs/testdiff/replacement.go`. It documents a regex whose behavior does not depend
on the exact version, and the version is masked to `[TF_PROVIDER_VERSION]` in
acceptance output anyway. Changing it is pure diff noise.

### Step 3: Regenerate the Go schema (with the registry-lag workaround)

The codegen tool (`bundle/internal/tf/codegen`) runs `terraform init`, which pulls
the provider from the **Terraform Registry** (`registry.terraform.io`). A freshly
published GitHub release is **not indexed by the registry immediately** — indexing
lags the GitHub release by anywhere from ~30 min to a few hours. If the registry
hasn't indexed the target version yet, `terraform init` fails with:

```
Could not retrieve the list of available versions for provider
databricks/databricks: no available releases match the given constraints {version}
```

First try codegen directly:

```bash
cd bundle/internal/tf/codegen
rm -rf ./tmp
go run .
```

**If it fails with the "no available releases" error above**, set up a local
filesystem mirror from the GitHub release (which always exists) and point Terraform
at it via `TF_CLI_CONFIG_FILE`:

```bash
# Download the provider zip from GitHub into a filesystem-mirror layout.
MIRROR=/tmp/tf_mirror
DIR="$MIRROR/registry.terraform.io/databricks/databricks"
mkdir -p "$DIR"
gh release download v{version} --repo databricks/terraform-provider-databricks \
  --pattern 'terraform-provider-databricks_{version}_linux_amd64.zip' \
  --dir "$DIR" --clobber

# Tell Terraform to resolve databricks/databricks from the mirror, everything else direct.
cat > "$MIRROR/cli.tfrc" <<EOF
provider_installation {
  filesystem_mirror {
    path    = "$MIRROR"
    include = ["registry.terraform.io/databricks/databricks"]
  }
  direct {
    exclude = ["registry.terraform.io/databricks/databricks"]
  }
}
EOF

# Re-run codegen against the mirror.
cd bundle/internal/tf/codegen
rm -rf ./tmp
TF_CLI_CONFIG_FILE="$MIRROR/cli.tfrc" go run .
```

Adjust the `linux_amd64` arch in the download pattern and the mirror path if you are
on a different platform (e.g. `darwin_arm64`). Codegen still fetches the real GitHub
SHA256 checksums for `root.go`, so nothing is faked — the mirror only shortcuts the
registry version lookup.

Then format the generated Go and clean up the mirror:

```bash
cd ../../../..          # back to repo root
gofmt -s -w bundle/internal/tf/schema
rm -rf /tmp/tf_mirror
```

A codegen line like `Warning: Skipping file generation for
databricks_quality_monitor to avoid known unwanted changes` is expected — leave it.

### Step 4: Regenerate the DABs↔TF field map

```bash
./task generate-schema-map
```

This updates `bundle/terraform_dabs_map/generated.go`. It reflects the schema delta:
a field the provider **added** that DABs already had leaves the DABs-only set; a field
the provider **removed** that DABs still supports moves into the DABs-only set.

### Step 5: Build

```bash
go build ./...
```

### Step 6: Refresh acceptance goldens — then VERIFY

Regenerate the goldens:

```bash
go test ./acceptance -run '^TestAccept$' -update -timeout=60m
```

**CRITICAL: `-update` alone can mask a real failure. Always follow it with a
non-update verify pass:**

```bash
go test ./acceptance -run '^TestAccept$' -timeout=60m
```

Why this matters: the acceptance harness (`acceptance/install_terraform.py`)
downloads the provider from GitHub keyed to `version.go`, so tests run against the
real new provider. Most bundle tests run under an `EnvMatrix` of both engines
(`terraform` and `direct`). When a schema change makes one engine error while the
other still succeeds, the two variants produce **different** output. `-update` runs
both and each overwrites the other's `output.txt`, so it can silently land on the
passing variant's output and report `ok` — hiding the failure. The verify pass runs
each variant against the committed golden and catches the divergence.

The full verify run also emits blocked-proxy log lines (`rejecting_proxy.go: blocking
proxy: ...`) — that is normal and not a failure. Grep for `--- FAIL` / `FAIL\t` to
find real failures. A lone test that times out under full-suite parallel load but
passes in isolation (`go test ./acceptance -run 'TestAccept/<path>'`) is a flake, not
a regression — re-run it alone to confirm.

### Step 7: Resolve behavior changes the verify pass surfaces

If Step 6's verify pass fails, the provider schema changed in a way that affects a
test. Diff the generated schema to understand what changed
(`git diff bundle/internal/tf/schema/resource_<x>.go`), then adapt the **test**, not
the generated code. Common shapes:

- **A field became required** → the terraform engine now rejects a fixture the direct
  engine still accepts (divergent variants). Fix the fixture `databricks.yml` so it is
  valid under the new schema (add the now-required field), making both engines produce
  identical output again. Look at sibling tests for the correct field shape.
- **A field was removed** from the provider but the CLI/direct engine still supports it
  → the terraform engine emits `Warning: unknown field: <field>` and drops it. If the
  feature is only meaningful on the direct engine now, restrict the test to it with a
  comment explaining why:

  ```toml
  # The Terraform provider dropped `<field>` in v{version}, so this feature is
  # only exercisable via the direct engine.
  EnvMatrix.DATABRICKS_BUNDLE_ENGINE = ["direct"]
  ```

  Then regenerate that test's output and `out.test.toml`:
  `go test ./acceptance -run 'TestAccept/<path>' -update`.

Do not edit generated `out*` files by hand — regenerate them. Re-run the single test
in both `-update` and verify mode until it is green, then re-run the full verify pass.

### Step 8: Add a changelog fragment

Create `.nextchanges/dependency-updates/tf-provider-{version}.md`:

```
Bump Terraform provider from v{old_version} to v{version}.
```

(Leave the PR-number link out for now — you add it after the PR exists, in Step 10.)

### Step 9: Format, lint, commit, push, and open the PR

```bash
./task fmt
./task lint-q
```

`gofmt`/`fmt` and lint should be clean; if they touch `acceptance/`, a source fixture
is wrong — fix it and regenerate rather than editing output.

Commit (the CLI repo pushes to `databricks/cli`, which may need a `gh` account with
write access — if `git push` 403s, run `gh auth switch --user <writer>` first):

```bash
git add -A
git commit -F - <<'EOF'
Bump Terraform provider to v{version}

## Changes

Bump the pinned Databricks Terraform provider from v{old_version} to v{version}.

Notable schema changes:
- <one short bullet per user-visible resource/field change; keep it terse>

## Tests

Acceptance goldens regenerated via `./task test-update`.

Co-authored-by: Isaac
EOF
git push -u origin HEAD
```

Then open the PR (respect the user's global rules — if they require explicit
permission before creating a PR, ask first; a draft PR is a good default):

```bash
gh pr create --draft --base main --title "Bump Terraform provider to v{version}" --body "$(cat <<'EOF'
## Changes

Bump the pinned Databricks Terraform provider from v{old_version} to v{version}.

Notable schema changes:
- <same terse bullets as the commit body>

## Tests

Acceptance goldens regenerated via `./task test-update`.
EOF
)"
```

### Step 10: Backfill the PR link and mark ready

Once the PR number exists, add it to the changelog fragment and expand the link:

```bash
# edit .nextchanges/dependency-updates/tf-provider-{version}.md to end with " (#{pr_number})."
./task links   # expands (#NNNN) into a full markdown link; CI fails on an unexpanded one
git add .nextchanges/dependency-updates/tf-provider-{version}.md
git commit -m "Add PR link to changelog fragment"
git push
gh pr ready {pr_number}   # only if you opened it as a draft and the user wants it ready
```

Report the PR URL to the user.

## Summary of what to touch (and what not to)

Edit by hand:
- `bundle/internal/tf/codegen/schema/version.go` — the only hand-edited source.
- Acceptance fixtures / `test.toml` that break on the schema change (Step 7).
- `.nextchanges/dependency-updates/tf-provider-{version}.md` — new fragment.

Generated — never hand-edit (regenerate via the commands above):
- `bundle/internal/tf/schema/*` (including `root.go`), `bundle/terraform_dabs_map/generated.go`,
  and any `acceptance/**/out*` goldens.

Do not touch:
- The version comment in `libs/testdiff/replacement.go`.
- `CHANGELOG.md` (generated from fragments at release time).
